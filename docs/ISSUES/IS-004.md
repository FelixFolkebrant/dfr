# Issue

### What?

IS-004: Load one selected file patch through the Git backend.

This issue adds lazy, extension-host patch loading for one file selected from a merge-base comparison. It returns text patches or binary metadata while keeping webview state, rendering, caching, and patch-size policy out of scope.

### Acceptance criteria

- [x] Stable selected-file patch input and result types are defined behind the internal Git backend boundary.
- [x] Patch loading uses `git merge-base <base> <head>` followed by a path-scoped diff from the merge base to the head ref.
- [x] Text patches are returned without loading patches for other changed files.
- [x] Rename requests retain and pass both old and new paths to Git.
- [x] Binary files are identified without returning binary diff text as a renderable patch.
- [x] Git commands continue to use argument arrays without shell interpolation.
- [x] Missing patches and Git failures produce actionable errors with file and comparison context.
- [x] Webview messaging, rendering, caching, and patch-size policy remain out of scope.
- [x] Focused automated tests and all repository checks pass.

### Notes

- The patch command disables external diff drivers and text conversion so results remain deterministic and binary detection remains explicit.
- The existing 80-line unified context from the product specification is used.
- Extension-to-webview selected-file messages are planned for a later issue.

# What has been built

The internal Git backend now loads a single selected file patch using the same merge-base semantics as comparison summaries. Requests can include both paths for renamed files. Text files return their raw unified patch, while binary files return an explicit binary marker without patch text.

Patch commands are path-scoped, use argument arrays, and disable external diff and text-conversion behavior. Empty output and Git failures report the selected path, merge base, and head ref.
